# Version 0.5 one-hour resource soak — 2026-08-30

This run exercised the installed version 0.5/build 8 lossless whole-frame DPCM
sender and receiver continuously for 3,600 seconds on the target MacBook and
the exact 2017 27-inch iMac. It is recorded as a **qualified failure**: the
connection, storage, descriptor, thread, and thermal-pressure gates passed,
but the receiver exceeded the project's strict post-warm-up RSS-slope gate.
Version 0.5 is therefore not the release candidate.

This is also not immutable release proof. The collector recorded source
revision `01b0f6290379d1729ab7fc8e822690974d68fb8b` with `worktree=dirty`.
The exact installed executable identities were:

- MacBook sender SHA-256:
  `7c42354be31cd95af59c4c2d2f0e08c4c0bf9dfa6e5db0a0c66543dc2b181ffe`;
- iMac v0.5/build 8 receiver SHA-256:
  `cc1c7e15ec16164aef2a4fd79da0a1bd76b807fd6ecfdfe4be960f725e1774d2`.

Those hashes make the installed processes identifiable, but the dirty source
state still disqualifies this run from reproducible-release status.

The privacy-scrubbed samples are in
[`2026-08-30-v0.5-resource-soak.tsv`](2026-08-30-v0.5-resource-soak.tsv).
The final regression below excludes the first 1,200 seconds, after the
sender's one-time resident-memory step, and uses 41 samples over 2,400 seconds.

|---|---:|---:|---:|---:|---:|---:|
| MacBook sender | 39.36% | 50.80% | 218,112 → 218,224 KiB | +0.247 MiB/hour | 11–14 | 19 |
| iMac receiver | 49.61% | 57.50% | 101,184 → 104,248 KiB | +4.460 MiB/hour | 7–8 | 15 |

The final-30-minute window measured +0.091 MiB/hour for the sender and +4.435
MiB/hour for the receiver. All 61 samples found both processes running.
Application-bundle, Application Support, and log sizes were exactly flat; no
frame data was written to disk. Neither Mac reported a thermal or performance
warning. The MacBook remained on AC at 100%, so the run does not claim a
battery-energy measurement.

At the end of the run, `leaks` reported **zero leaked allocations and zero
leaked bytes** in the receiver (21,575 live allocation nodes). Its physical
footprint was 112.3 MiB. `vmmap -summary` attributed 63.6 MiB resident memory
to `IOAccelerator`; three IOSurface regions occupied 168.8 MiB of virtual
address space and zero resident bytes in that snapshot. The two fixed 64 MiB
receive buffers are intentional and bounded.

The restricted sender process reported 17,776 bytes in 315 Foundation,
AppIntents, and Network reference-cycle nodes. The sender's post-warm-up RSS,
thread count, descriptor count, and on-disk sizes nevertheless plateaued. This
is recorded as framework-level diagnostic evidence, not promoted to a claim of
zero sender leaks.

## Qualification

- **Pass:** 60-minute liveness, fixed file-descriptor and thread bounds, flat
  bundle/support/log storage, receiver heap-leak scan, and macOS thermal and
  performance-pressure checks.
- **Pass with expected cost:** continuous native whole-frame transport used
  about 39% of one MacBook CPU core and 50% of one iMac CPU core. macOS did not
  report thermal pressure, but this test does not measure fan RPM.
- **Pass:** sender steady-state RSS plateau after its one-time warm-up step.
- **Fail:** receiver steady-state RSS rose about 4.4–4.5 MiB/hour, above the
  project's 2 MiB/hour release gate despite no heap leak.
- **Not a visual acceptance run:** the iMac entered a secure login session
  during this unattended interval. Transport and rendering stayed live, but
  physical scanout, cursor ownership, and post-unlock recovery require a human
  observation on the replacement build.

Version 0.6 removed the version 0.5 saver-process polling/termination mechanism
and replaced it with public workspace-session and key-window lifecycle policy.
Its follow-up run still reproduced a memory staircase and isolated a separate
once-per-minute power-management call. Version 0.7 removes that redundant call
and requires its own full soak; neither prior result is reused as release proof.
