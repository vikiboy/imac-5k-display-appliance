# Version 0.9 lifecycle candidate — 2026-08-30

Version 0.9 addresses the failure exposed by the completed v0.8 soak: a
securely locked iMac had no presentable Aqua surface, yet both peers continued
capturing, encoding, transporting, decoding, and submitting 5K frames.

This record is a **receiver deployment and control-plane qualification**, not a
paired video-stream release pass. While the owner was asleep, the rebuilt
sender was installed but intentionally not launched: changing its ad-hoc code
identity requires one foreground Screen Recording approval, and the project
does not automate or reset TCC consent. The prior sender remains available as a
single rollback bundle.

## What changed

- optional receiver-surface (`0x39`) and source-display (`0x3A`) packets with
  monotonic epochs and an ordered receiver-epoch acknowledgement barrier;
- capture, DPCM/Metal, audio, and frame-network work pause while either source
  or receiver display surface is unavailable, while the virtual display,
  arrangement, and control connection remain alive;
- a black privacy cover, balanced local-cursor ownership, and display-awake
  assertion are all fail-closed behind public AppKit/NSWorkspace state;
- a newly usable surface remains covered until a frame from its exact current
  presentation generation actually completes;
- launch during an already locked session uses a read-only console snapshot,
  requires explicit unlocked evidence, does not wake the panel, and performs
  only bounded generation-cancelled recovery retries;
- malformed, signed, stale, conflicting, or overflowed lifecycle epochs and
  malformed/ambiguous console records cannot authorize pixels or cursor hiding;
- fixed receive slots, cached drawable geometry, bounded rolling timing data,
  and non-allocating hot-path renderer statistics preserve the resource bounds.
- build 17 additionally limits global arrow-cursor restoration to the active
  key appliance window. Its AppKit unit fixture now matches the production
  window's ARC ownership instead of relying on `NSWindow`'s self-release-on-
  close default.
- build 18 separates secure-session ownership from ordinary AppKit focus.
  Screen Sharing, a system panel, or transient key-window loss no longer
  blanks a live surface or releases the iMac cursor. Transparent cursor
  tracking remains window-scoped and active across non-key focus; the secure
  session-resign boundary still blanks pixels and balances every cursor hide.
- sender automatic mode now has a pre-LaunchServices marker gate plus an
  in-app marker gate, launches a new instance at the exact stable path, and
  cannot speculatively revive a user-stopped or permission-suspended stream;
- sender installation validates the final signature, bundle identifier, and
  executable before mutation, performs one marker-authorized bootstrap, and
  transactionally restores prior plist, marker, and display-sleep preference
  state after an ambiguous failure;
- sender uninstall and failed-install rollback terminate and verify the exact
  installed app rather than merely stopping launchd's waiting `open` process.

The receiver intentionally retains one `PreventUserIdleSystemSleep` assertion
while waiting so it remains reachable as a display appliance. It does not hold
`UserIsActive` or `PreventUserIdleDisplaySleep` while idle, so the panel may
sleep and no cursor is hidden. This is an explicit availability-versus-idle-
power tradeoff, not a leak.

## Live receiver probe and installed-idle verification

A frame-free probe against build 16 connected over the direct link and
received:

| Field | Value |
|---|---:|
| Physical panel | 5120 × 2880 |
| Logical mode | 2560 × 1440 HiDPI |
| Requested refresh mode | 60 Hz |
| Raw DPCM | supported |
| Display lifecycle | supported |
| Initial receiver surface | available, epoch 2 |

The probe echoed that receiver epoch in an awake source-state packet, sent a
heartbeat, and disconnected. No capture or image payload was used. Build 16
then measured **0.0% CPU, 12 MiB RSS, and 6 threads** and held no display-awake
or user-active assertion.

Build 17 changes only the non-key cursor restoration guard and its AppKit test
ownership. After an atomic receiver upgrade, its installed signature and hash
matched the staged universal app, the LaunchAgent and listener each had one
running instance, and the idle listener measured **0.0% CPU and approximately
18.6 MiB RSS**. `UserIsActive` and `PreventUserIdleDisplaySleep` remained zero;
only the fixed system-availability assertion remained active as designed. This
post-install check is not a substitute for a new video-frame acceptance run.

Build 18 was installed transactionally after the later focus/cursor diagnosis.
Its staged and installed hashes match, its strict deep signature verifies, and
its launch agent owns exactly one receiver process. While the owner remained
away, macOS reported `IOConsoleLocked=Yes`, the built-in 5120 x 2880 panel as
online but asleep, and the receiver at **0.0% CPU and approximately 18 MiB
RSS**. It held only the fixed system-availability assertion: `UserIsActive` and
`PreventUserIdleDisplaySleep` were both zero. The appliance screen-lock setting
was already `off`, but macOS correctly does not retroactively unlock an
existing secure session.

After the later observed ScreenShare/black-cursor transition, a quiet SSH retry
returned `No route to host`. A contemporaneous MacBook hardware inventory
enumerated only the Dell U3425WE on Thunderbolt/USB4; the iMac was not an active
Thunderbolt peer and the local bridge was inactive. No sender, receiver test,
debugger, or benchmark process was running on the MacBook. Consequently that
black/off state is evidence of an absent or sleeping physical peer, not evidence
of either successful streaming or a regression in the new frame lifecycle.

A later Wi-Fi-side inspection refined that diagnosis without weakening it: the
iMac remained reachable, and its own Thunderbolt controller still reported an
active bridge, while the MacBook did not enumerate the iMac as a Thunderbolt
peer. The black screen with a cursor was the already-locked macOS session, not
a live receiver image. Build 18 deliberately does not draw over, synthesize
input into, or otherwise bypass that secure layer.

One recovery edge remains explicit rather than hidden: if the receiver process
itself restarts while the iMac is already securely locked, it waits for a normal
unlock before creating a drawable surface and listener. A future listener-first
control plane may accept a validated Thunderbolt HELLO and issue one public
display-wake request while still advertising `surface=false`, but it must never
expose pixels before the ordinary Aqua session becomes eligible. The current
dedicated-appliance setting prevents a normal display-idle event from creating
a new lock after the owner performs the one existing unlock.

The stale sender job was subsequently disabled through the reversible
uninstaller before the final sender was atomically replaced. Four superseded
historical sender bundles (approximately 29 MiB total) were removed; one known
pre-v0.9 rollback remains beside the 7.5 MiB installed sender.

3. Confirm plug-in automatic reconnect and the native macOS arrangement with
   the Dell/power connection present.
4. Physically verify lossless Retina text, clicks/drags/Spaces, one cursor only,
   and no iMac Dock/menu/screen saver leaking over the stream.
5. Run lock/unlock, MacBook display sleep/wake, iMac panel sleep/wake, cable
   unplug/replug, and app-restart recovery. Every resume must wait for a fresh
   current-generation presentation.
6. Repeat corrected synchronized cadence A/B and the one-hour active-surface
   resource soak. The receiver RSS slope gate remains no greater than
   +2 MiB/hour after warm-up, with flat descriptors, threads, app/support/log
   storage, no thermal warning, and no presentation-integrity error.

Until those physical gates pass, v0.9 is a promising staged candidate rather
than a production-complete monitor replacement.
