# iMac 5K Display Appliance: 2017 27-inch setup

This note covers the 2017 27-inch Retina 5K iMac (`iMac18,3`) as a receiver for
a modern Mac running this independent TargetBridge derivative. It does not
claim support for every iMac generation or configuration.

TargetBridge does not restore Apple's hardware Target Display Mode. The iMac
continues to boot and run macOS, and a receiver app presents pixels sent by a
separate sender app. The case stays closed: no panel controller board, internal
cable change, or other iMac disassembly is required.

## Two-app architecture

Two logged-in Macs participate in every session:

1. **TargetBridge Sender** runs on the source Mac. It creates an extended
   virtual display (or captures a mirror), captures that display, and sends the
   resulting frames over a network interface.
2. **TargetBridge Receiver** runs on the 2017 iMac. It listens for the sender,
   renders incoming frames fullscreen on the built-in panel, and returns
   receiver capability information.

Because the iMac remains a Mac rather than becoming a passive video input, it
can continue to provide services such as SSH or file sharing while receiving a
display stream. Heavy concurrent work can still affect display latency.

While no sender is connected, the waiting receiver prevents unintended system
sleep but lets the panel follow the iMac's ordinary display-sleep setting. Once
a display session is active, it adds a display-awake assertion and user-activity
lease so the panel behaves like a connected monitor and stays on. A panel that
turns off during an active stream is a failure; a panel that sleeps while merely
waiting is expected and saves power.

Version 0.9/build 19 handles a receiver restart while that panel is asleep with
a small listener-first control plane. Discovery and throughput probes remain
wake-inert. A real display HELLO is accepted only when both socket endpoints
are link-local and the iMac endpoint belongs to `bridge0`; that HELLO requests
one bounded wake, after which the Sender retries into the full native-Metal
listener. The retry is finite and works for both the GUI Connect button and
automatic appliance mode. This does not unlock an already secure macOS session.

## What “5K Retina” means

The intended extended-display mode is **2560 × 1440 logical points** with a
strict **2× 5120 × 2880 pixel backing store**. Applications lay out their UI in
2560 × 1440 points; macOS renders each point with a 2 × 2 pixel backing grid for
Retina text and controls. This is native panel geometry, not a 2560 × 1440
frame enlarged to fill the screen.

Geometry and color fidelity are separate. For the measured fidelity run,
ScreenCaptureKit produced an 8-bit BGRA raster and TBD2/DPCM carried its
full-resolution RGB channels losslessly. It does not enlarge, sharpen, or
synthesize pixels. The sender fixes capture to SDR Display P3 and the receiver
labels the Metal layer as Display P3 so macOS can color-manage the frame for the
iMac panel. The separate raw diagnostic carries NV12/4:2:0 and is not the
native-text-quality target. Do not collapse those two formats into a claim of
one generic raw full-RGB path. The appliance profile fails closed if DPCM is
unavailable; it does not silently downgrade to NV12.

## Cable and connection behavior

Use a certified Thunderbolt 3, 4, or 5 cable connected to a Thunderbolt port on
both Macs. The 2017 iMac is a Thunderbolt 3 endpoint, so a newer cable cannot
raise the negotiated link beyond the capabilities of that iMac.

The project hardware uses the **Anker A8859, 0.7 m Thunderbolt 4 cable** from
the owner's Amazon order (ASIN `B095KSL2B9`). Anker identifies A8859 as a
40-Gbit/s Thunderbolt 4 cable. That cable is already the correct class for this
setup; replacing it with Apple's Thunderbolt 5 cable would not upgrade the
2017 iMac's Thunderbolt 3 controller. A replacement is warranted only if a
link test shows instability or a damaged cable, not as a prerequisite for this
software path.

The display stream is carried as IP traffic over **Thunderbolt Bridge**; the
cable is not feeding DisplayPort video into the iMac. A healthy direct link may
report a 40 Gb/s Thunderbolt physical rate, while application-level TCP
throughput is necessarily lower. The recorded direct TCP test on this exact
setup measured **17.06 Gbit/s**; that is an observed application-level result,
not a claim that the 40 Gbit/s link rate is usable payload bandwidth.

Some reconnects can expose a direct cable as USB-NCM networking instead of a
true Thunderbolt Bridge path. USB-NCM is a useful encoded-stream fallback, but
it should not be expected to sustain lossless 5120 × 2880 whole-frame transport
at a 60-frame/s target. The
appliance profile therefore requires the receiver's explicitly advertised
Thunderbolt address together with the MacBook's local `bridge0` interface, then
lets the real monitor socket be the reachability check. It fails closed rather
than silently choosing Wi-Fi, Ethernet, or USB. The separate cable diagnostic
can measure throughput on demand; it is not rerun on every reconnect because
that would add startup work and temporarily occupy the single-client receiver.
Encoded or lower-resolution profiles remain available outside this dedicated
appliance path.

## One-time setup

1. Install and launch TargetBridge Receiver on the iMac.
2. Install and launch TargetBridge Sender on the source Mac.
3. When macOS asks, grant **Screen Recording** to the installed Sender app.
   Quit and reopen the app if macOS requests it. Local Network permission may
   also be requested for discovery and the direct connection.
4. Enable Thunderbolt Bridge in Network settings on both Macs and connect the
   cable while both machines are awake and unlocked.
5. Start the receiver first, then connect from the sender using **Extended
   display**. Arrange the virtual display in **System Settings → Displays**.

Input Dockstation features are optional and can require Accessibility or Input
Monitoring permission on one or both Macs. They are not required merely to
show the extended desktop.

After first-time permissions and display arrangement are complete, login items
or LaunchAgents can start the two apps and reconnect automatically. A logged-in
graphical session is still required on both machines.

The appliance launch agents preserve stable installed paths so macOS Screen
Recording consent remains associated with a stable sender TCC identity. On the
iMac, installation disables the local screen saver while the appliance is
installed and saves the previous setting for uninstall. Changing screen-lock
policy is a separate explicit opt-in and is likewise backed up and reversible.
These settings do not unlock an already-locked graphical session. Such a session
still needs one physical unlock before the foreground cursor can be judged. In
that state, a black
panel with only the iMac's local cursor is the protected macOS login surface;
it can cover an otherwise connected, rendering receiver. The app intentionally
does not bypass that security boundary and should reclaim its surface after the
physical unlock.

In the current source-compatible build, the privacy pane calls the sender
**TargetBridge** even though its visible app name is **iMac 5K Display Sender**
and its derivative identity is `com.vikiboy.imac5kdisplay.sender`. Use the 5K
monitor icon and add the exact stable app path with the pane's **+** button only
on a clean first installation when macOS did not create the row. Do not remove
or reset either existing **TargetBridge** row on the accepted machine: the
labels are ambiguous and the current certificate-backed grant is working. A
permission prompt on every launch is not an accepted steady state.

The receiver must be a normal foreground AppKit application before it hides the
iMac's local cursor. Automated tests cover that contract and cleanup. The owner
physically confirmed one cursor plus normal clicking and selection in a live
Retina session; disconnect restoration remains a separate lifecycle gate.

## Current experimental limitations

- Native lossless 5K in a 60 Hz display mode is an experimental software
  transport, not a zero-latency hardware display input or proof of 60 evenly
  spaced presentations each second. Capture, copying, transport, and
  presentation each add latency.
- The measured fidelity format is lossless 8-bit BGRA-to-TBD2/DPCM with
  full-resolution RGB channels. It preserves the captured RGB raster exactly,
  but it is not a 10-bit/HDR transport. ColorSync,
  panel calibration, brightness, Night Shift, and True Tone can still make the
  physical panels look different, and gradients may not match a 10-bit path.
- DPCM compression is content-dependent. Normal desktop frames are expected to
  fit the measured single-cable path; high-entropy full-screen content can exceed
  it and still needs sustained end-to-end characterization.
- Cable insertion alone cannot display the source Mac at the iMac login screen,
  FileVault unlock screen, Recovery, or before the receiver user logs in.
- The corrected five-minute hardware A/B measured 58.376 presented FPS for the
  serial receiver and **59.972 presented FPS** for the bounded two-slot receiver
  from a 59.983 Hz source. The selected mode had one drop, 16.8 ms p99, a
  33.376 ms maximum gap, and zero malformed/queue/GPU/renderer/order errors. It
  uses two fixed 64 MiB receive slots, not an accumulating frame queue.
- Live MacBook display sleep/wake and a physical Thunderbolt cable
  unplug/replug both automatically restored the same native 5K extended
  display. Build 19 fails closed while the true Thunderbolt path is absent. An
  already locked iMac still requires an ordinary physical unlock, and other
  cable/fallback topologies remain outside the accepted configuration.
- The verified scope is the 2017 27-inch 5K iMac configuration named above.
  Other GPUs, macOS versions, iMac models, and sender Macs require their own
  sustained and visual validation.
- The completed whole-frame resource soaks were qualified failures: the initial
  baseline measured +6.251 MiB/hour receiver RSS, while installed v0.5/build 8
  improved to +4.460 MiB/hour after warm-up. Version 0.6/build 10 then
  reproduced a +7.363 MiB/hour post-warm-up staircase. Version 0.7 removed its
  redundant once-per-minute power call, then isolated a separate bounded
  telemetry page ramp and was deliberately perturbed for heap inspection.
  Version 0.8/build 13 completed 3,600 seconds with flat sender RSS, threads,
  descriptors, and disk use and no thermal warnings, but the receiver still
  measured +4.819 MiB/hour after 1,200 seconds. More importantly, the securely
  locked iMac completed zero physical presentations while both peers kept doing
  full-rate work. Version 0.9 therefore adds a fail-closed lifecycle handshake;
  its component and live control-plane probes pass; one-cursor, paired stream,
  source sleep/wake, and cable-reconnect acceptance also passed. The selected
  v0.9 overlap build still needs a one-hour active-surface RSS qualification
  before any broader production claim.
